# LLM能力与验证约束

版本日期：2026年11月3日

本约束用于后续代码修改、代码审查、测试验收和项目材料。当前实现的差距见`调研/LLM代码审查与整改清单_20261103.md`。书面约束通过AGENTS.md纳入开发要求，运行时校验仍按整改清单实施。

本轮已实现的校验与未覆盖范围见[整改结果](../调研/LLM约束整改与验证结果_20261103.md)。原审查清单保留问题发现时的代码状态。

## 能力定位

当前初始告警主要由静态规则、外部分析器、抽象解释和动态测试产生。LLM承担告警研判、检索后重判、函数补丁建议和测试驱动编译修正。规则驱动的规划、任务调度、监控和结果汇聚，按其实际实现说明。

后续可扩展LLM的检测职责，但新增能力必须有真实调用路径、输入输出契约、独立验证器和测试证据。只增加角色名称、提示词或日志，不计为新增检测能力。

## 结论与证据状态

| 状态 | 可以表达的含义 | 不能据此推导的结论 |
| --- | --- | --- |
| 模型建议 | LLM给出的TP、FP或需复核建议 | 漏洞已经证实或告警可以删除 |
| 引用有效 | 引用行在允许范围内，确为代码并包含告警位置 | 推理语义正确、路径可达或漏洞可触发 |
| 工具验证通过 | 指定工具在明确环境和假设下完成了对应验证 | 任意平台正确、程序整体安全或业务行为完全等价 |
| 人工确认 | 有记录的评审者完成该项判断 | 其他告警、其他版本也获得确认 |

原始告警、引擎、源码版本和工具证据必须保留。模型的研判结果作为附加状态保存，不能覆盖或伪造工具事实。

## 必须落实的代码约束

### LLM01严格解析模型响应

响应内容必须为字符串，解析后为符合结构契约的对象。置信度必须为非布尔、有限且位于[0,1]内的数值。证据行必须为非布尔正整数列表。拒绝NaN、Infinity、小数行号、非法字段类型和缺失的必需字段，不通过静默转换修补模型输出。

客户端响应、JSON解析和字段校验的异常应被限制在当前任务。保留可定位的失败原因，不让单条畸形输出中断整批扫描。

### LLM02对真缺陷和误报使用相同门槛

TRUE_POSITIVE与FALSE_POSITIVE均须满足上下文、证据和采纳条件。任一引用无效时，整条证据校验失败。需要保留原始引用与失败原因，禁止丢弃错误引用后将整体标记为通过。

上下文缺失、最终调用失败、最终解析失败和证据不合格统一转NEEDS_REVIEW，并将新状态回写告警，清除不再有效的旧研判。不得保留旧TP或FP继续参与修复、隐藏和报告统计。

### LLM03区分检索重判与最终采纳

检索触发阈值和最终采纳策略分别配置、分别测试。当前默认0.6仅是重判触发值，不能表述为已校准的正确概率。最终低置信结论保留需复核，或必须取得额外独立证据后再采纳。

有界重试必须保留每次调用的模式、结果与失败原因。首次失败后允许重试恢复，最终报告应如实记录恢复过程。

### LLM04记录实际上下文和检索来源

记录实际加载的文件、函数、源码范围、未解析调用和截断状态。不同入口应使用一致的上下文构建策略；跨文件函数尚未加载时，不能声称已经完成项目级上下文研判。

规则与CWE键匹配按键匹配描述。只有实际实现并验证相应检索链路后，才使用芯片手册检索、向量检索或语义检索等能力名称。

### LLM05逐项记录修复验证状态

静态重扫、编译、动态重放和行为回归分别保存PASS、FAIL、SKIPPED、UNSUPPORTED或ERROR。必需检查未完成时，不能输出“修复验证通过”。允许生成补丁建议，但必须标明尚待验证。

验证前确认原告警能在当前源码与配置下重现。验证后使用原规则、原引擎、相同硬件描述、编译参数和项目上下文重放。硬件、工程级和外部引擎告警，不能用文件规则扫描未返回该规则来证明其消失。

### LLM06检查补丁范围和新问题

核对函数名称、签名、边界和补丁修改范围，防止删除目标函数或整个函数体来消除告警。确需接口或行为调整时，作为显式设计变更处理并补充对应测试。

新增错误按告警实例、位置和类别比较。原来已有一条同规则错误，不能掩盖补丁新增的第二条。语法通过只证明语法层面的有限性质，业务行为保持须由对应测试与评审支撑。

### LLM07保留测试驱动的有效性

LLM修改harness后，程序化核对目标函数调用、参数激励入口、oracle和必要观测点仍存在，并验证测试确实执行到目标。返回一个可编译的空main函数不得被接受为有效测试驱动。

每轮编译失败使用该轮最新错误日志。记录harness修改、打桩、工具链和运行载体；修改后的测试环境不能冒充真实硬件执行。

### LLM08使用精确的动态证据关联

动态事件关联静态告警时，至少核对文件、函数、缺陷类别和证据位置，并给出关联依据。一个函数发生除零，不能证明同函数的寄存器权限问题已复现；一个文件中的同名函数崩溃，不能升级另一个文件的告警。

无法建立对应关系时，保存独立动态事件，原静态告警保持原状态。

### LLM09落实高危复核与入口一致性

error级误报建议默认待复核。自动接受策略如被显式启用，必须记录配置与采纳依据；无合格证据的模型FP不能因此成为已确认误报。复核队列需要实际控制处理状态，不能只增加日志。

CLI、Web、Orchestrator使用统一的验证与采纳条件。不得将未分诊告警默认解释为已确认TP；需要直接尝试修复时，标明“未确认告警的候选补丁”。

### LLM10记录模式与统一预算

区分Mock客户端、确定性假客户端和真实模型端点。记录模型标识、实际端点配置、调用状态和验证结果，日志不得包含密钥。真实模型的准确率、修复率与耗时须由真实运行单独测量。

统一预算覆盖首次分诊、检索重判、补丁生成和harness修正。并发数与修复目标数不能冒充总调用或费用预算。未实现预算熔断时，材料不得声称该机制已生效。

## 后续整改的验收用例

| 约束 | 必须通过的用例 |
| --- | --- |
| LLM01 | 非字符串content、NaN/Infinity、布尔与小数行号、缺字段均受控失败；其他告警继续执行 |
| LLM02 | 无证据TP与FP、混合有效和无效引用均转需复核；缺失文件覆盖旧TP/FP |
| LLM03 | 低置信重判后仍低置信、第二次失败及重试恢复均有明确最终状态与调用记录 |
| LLM04 | 无告警的被调函数文件仍能按策略加载；同名static函数、未解析调用与截断可追踪 |
| LLM05 | 编译器缺失、原规则不支持或无法重放不能标通过；W1C仍存在的补丁必须拒绝 |
| LLM06 | 删除函数、修改签名、新增同规则第二条错误被识别；有效最小补丁通过对应回归 |
| LLM07 | 空main、删除目标调用、移除观测点的harness拒绝；有效驱动保留激励并可执行 |
| LLM08 | 不同文件同名函数、同函数不同缺陷类型不交叉升级；可关联事件保存精确依据 |
| LLM09 | CLI、Web与编排路径的同一候选得到一致状态；高危复核不能被入口默认值绕过 |
| LLM10 | 分诊、重判、补丁和harness共同扣减预算；Mock结果带模式标识 |

验收时应分别给出失败复现、修改后的结果和未执行项。已有常规测试通过，不替代这些针对性用例。
