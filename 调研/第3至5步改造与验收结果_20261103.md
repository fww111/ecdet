## 二、第3步：libFuzzer

### 2.1 已实现功能

- `LibFuzzerEngine`接收工程、驱动文件、额外源码和语料；支持明确的工具路径或`ECDET_CLANG`。
- `generate_byte_harness`为`int/void function(const uint8_t *, size_t)`接口生成`LLVMFuzzerTestOneInput`驱动模板。复杂硬件接口使用对应的显式驱动。
- 同时启用SanitizerCoverage、AddressSanitizer和UndefinedBehaviorSanitizer，限制执行次数、输入长度与运行时间。编译、运行和重放分别有超时保护。
- 保存工具版本、编译与执行命令、源码和可执行文件哈希、语料、覆盖记录、错误输入与重放日志。
- 只有保存的输入在同一可执行文件下独立重放并再次触发错误，才生成`ECDET-FUZZ-CRASH`告警，状态为Detected。
- 缺工具、编译失败、超时、缺少覆盖记录和无法重放分别保留状态。没有精确栈帧时明确标注位置不可用，报告定位到驱动入口。

### 2.2 真实工具验收

本机Visual Studio目录中的LLVM没有Clang编译器，已将LLVM-MinGW便携工具链下载到项目外侧的独立验证目录。实际编译器为Clang 23.1.4。

首次按`-fsanitize=fuzzer`编译时，Windows GNU目标明确拒绝该选项。随后为该目标增加显式compiler-rt链接路径，并保留覆盖率、ASan和UBSan插桩；具体参数与运行库哈希写入证据。未将不支持的编译视为验证通过。

| 样例 | 最终结果 | 独立证据 |
| --- | --- | --- |
| `packet_bad.c` | FINDING，1条动态告警 | 最终验收在22次执行内触发越界；错误输入保存后重放再次触发 |
| `packet_fixed.c` | COMPLETED，0条动态告警 | 实际完成5000次执行；保存覆盖计数与语料 |

覆盖计数来自实际插桩。最终错误版记录5个覆盖计数，修复版记录6个；两个版本的控制流不同，计数用于各自运行留痕。输出目录中的语料会复用于后续执行，因此发现次数与初始覆盖会受已保存语料影响。

实际验证范围是这两个字节解析样例及配置预算。修复版结果表示本次运行未触发错误。

## 三、第4步：Z3

### 3.1 已实现功能

`analyze_constraints`直接解析C源码，提取受支持函数的局部定长数组、标量参数、局部赋值、条件分支、早返回和数组访问。模型处理8/16/32位整数、C整数提升、混合有符号与无符号比较、无符号回绕，以及有符号运算的定义条件。

模型明确采用8位字节、16位short、32位int和二进制补码。循环、调用、指针、除法、移位、宏配置、实现相关转换和其他不支持结构会留下显式状态；源文件规模、函数数、访问数与分支数也有边界。

| 状态 | 报告含义 |
| --- | --- |
| SAT | 当前模型存在可到达越界访问的候选输入，输出Suspected告警 |
| UNSAT | 当前访问在记录的受限局部模型中没有越界输入 |
| UNKNOWN | 求解未得到确定结果，保留原因 |
| UNSUPPORTED | 源码或语义超出支持范围，例如前序有符号溢出 |
| UNAVAILABLE / ERROR | 缺少依赖或后端执行错误 |

每个访问保存源码位置、哈希、输入位宽、候选输入及SMT。已有告警保持独立，局部UNSAT不删除原告警。`--timeout-ms`限制单次求解时间，单个任务可以包含多次求解。

### 3.2 真实源码验收

实际使用Z3 5.3.3，Python包固定为`z3-solver==5.3.3.0`。

| 函数场景 | 实际结果 |
| --- | --- |
| 仅检查下标小于8，遗漏负数检查 | SAT，生成负数输入 |
| 同时检查下标的上下界 | UNSAT |
| 8位无符号参数255先提升，再加1访问256项数组 | SAT，下标为256 |
| 32位无符号最大值加1 | UNSAT，模型正确计算回绕为0 |
| 下标表达式依赖有符号溢出 | UNSUPPORTED |
| 设置极小求解资源预算 | 真实得到UNKNOWN |

另外编译并运行独立C程序，核对候选输入的分支、下标运算和无符号回绕，结果通过。该程序验证输入与算术关系，没有执行越界内存读取；SAT候选因此继续保持Suspected。

## 四、第5步：Renode

### 4.1 已实现功能

`RenodeRunner`支持显式路径或`ECDET_RENODE`，接收ELF、REPL、UART标识、输入字节、预期输出和失败标记。它保存工具版本、固件与平台哈希、源码哈希、执行脚本、独立UART文件和进程日志。

运行状态由进程退出、随机脚本完成哨兵、UART文件和输出判据共同决定。命令回显和进程日志不会被当成固件输出。只有UART实际输出显式失败标记，才生成`ECDET-RENODE-ORACLE`固件级Detected事件；缺少预期文本使验收失败，加载错误或超时保持ERROR或TIMEOUT。

本轮同时修复旧源码动态引擎忽略`carrier`参数的问题：显式请求Renode时，源码harness引擎会提示使用`firmware`入口，避免实际执行宿主程序却被解释为固件仿真。

### 4.2 真实固件验收

使用Renode 1.17.0便携版和Clang交叉编译的自写Cortex-M4裸机固件。平台描述包含最小STM32F4 CPU、内存、NVIC和USART2模型。

| 场景 | 实际结果 |
| --- | --- |
| 正常固件启动并接收字节`s` | PASS；UART观察到`ECDET_BOOT_OK`与`ECDET_STATUS_OK` |
| 故障宏固件接收同一字节 | FAIL；UART出现`ECDET_SELFTEST_FAIL`，输出1条Detected事件 |
| 错误REPL、错误ELF、不存在的UART | 均为ERROR，0条缺陷告警 |
| 已启动固件后超过6秒墙钟预算 | TIMEOUT，0条缺陷告警；结束后剩余Renode进程为0 |
| 输出目录包含空格 | 正常通过 |

Renode下载包的SHA-256与官方GitHub资产digest一致。当前验证的是最小STM32F4模型上的启动与UART交互，其他外设、中断场景和真实硬件运行需要各自验收。

## 六、本机复现

以下命令在`ecdet`目录执行，使用本轮增强环境和独立工具目录。

```powershell
$python = (Resolve-Path '../ecdet本地检查/reuse_audit_20261103/.venv/Scripts/python.exe').Path
$clang = (Resolve-Path '../ecdet本地检查/steps345_20261103/tools/llvm-mingw-20261020-ucrt-x86_64/bin/clang.exe').Path
$renode = (Resolve-Path '../ecdet本地检查/steps345_20261103/tools/renode-1.17.0/renode_1.17.0-portable/renode.exe').Path

& $python -m ecdet constraints examples/constraints_demo/bounds.c
& $python -m ecdet scan examples/constraints_demo --no-build --constraints

& $python scripts/validate_libfuzzer.py --clang $clang --output-dir ecdet_reports/fuzz_validation
& $python -m ecdet fuzz examples/libfuzzer_demo --harness harness.c --source packet_fixed.c --clang $clang --runs 5000 --timeout 20

& $python scripts/validate_renode.py --clang $clang --renode $renode --output-dir ecdet_reports/renode
& $python -m ecdet firmware ecdet_reports/renode/good/firmware.elf --platform examples/renode_demo/stm32f4_minimal.repl --renode $renode --input-hex 73 --expect ECDET_BOOT_OK --expect ECDET_STATUS_OK --failure-marker ECDET_SELFTEST_FAIL
```

源码动态引擎的原有测试方式继续可用。新增功能以明确入口执行，不要求调用LLM。工具下载和安装位于独立验证目录，没有修改系统PATH；本轮未commit或push。
