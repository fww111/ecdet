# LLM代码审查与整改清单

审查日期：2026年11月3日

整改进展：本清单保留审查时的发现，后续代码修改与393项测试结果见[整改结果](LLM约束整改与验证结果_20261103.md)。

队友截图对LLM“告警研判和修复助手”的定位基本准确。代码确实存在低置信度检索重判、函数补丁建议和harness修正路径。但截图中“输出失败、调用失败或证据不合格都会转需复核”的说法超出了实际保障，修复验证也有可复现的误通过。

本次完成只读代码审查、隔离探针与约束文件落地。发现的问题尚未修改生产实现，下面明确区分代码现状与整改要求。

## 截图逐项核对

| 截图中的说法 | 审查结论 | 代码实际情况 |
| --- | --- | --- |
| LLM主要承担告警研判和修复辅助 | 基本成立 | 初始告警来自静态、动态和工具组件；LLM接收候选并给出建议 |
| 读取函数、相关调用和宏，给出TP、FP或需复核 | 有实现，有范围限制 | 切片按函数名展开最多两层调用；CLI分诊只加载有告警的文件，其他被调函数文件可能缺失 |
| 置信度低于0.6时检索再判断一次 | 默认路径成立 | 阈值可配置；知识库按规则与CWE匹配规则元数据和GJB主题；第二次仍低置信时也可能保留TP |
| 生成函数补丁，再做静态重扫和编译检查 | 有实现，验证范围有限 | FixVerifier只重放FILE_RULES；gcc可选，缺失时仍可能标记verified |
| 编译失败时修正测试harness | 有实现，约束不完整 | 修改后重新编译，但没有强制检查目标调用与激励是否保留 |
| 失败或证据不合格都会转需复核 | 不成立 | FP证据失败未降级；部分畸形响应与修复调用失败会抛异常；缺失上下文时旧结论可能残留 |

首次解析或调用失败后，分诊会以低置信度触发重试，第二次成功时可恢复。因此可准确描述为“部分分诊失败路径有重试与降级”，不能描述为所有LLM路径已具备完整保护。

## 源码确认的其他差距

- `agents.py:73`将auto_accept默认为True。高危FP会进入队列并记录自动接受标志；该队列当前不能当作强制人工复核已经生效的证据。聚合层仍保留原告警，本次未发现队列直接删除告警的行为。
- `agents.py:93`的预算只有修复目标数和并发数，没有覆盖全部LLM路径的统一调用或费用熔断。
- `cli.py:257`对未分诊告警默认按TP进入修复候选，不能表述为仅修复已经确认的缺陷。
- `webui/runner.py:389`至392另设验证逻辑，编译默认值为通过，没有使用与FixVerifier完全相同的采纳条件。此项按源码审查确认，未执行Web写入分支。
- `html_report.py:118`将分诊区标为“证据行号核对后”，并使用“确认为真实告警”等文字。当前verified只代表引用位置校验，不能支撑语义正确或漏洞已证明的表述。
- 规划、调度、运行时监控和汇聚包含确定性实现。六类模块存在，不等于六个LLM分别完成自主推理。
