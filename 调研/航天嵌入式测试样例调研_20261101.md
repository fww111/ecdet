## 五、调研报告（V1.2 docx）重点标注

> 以下为《嵌入式软件代码缺陷与安全漏洞检测系统调研与技术方案V1.2》中会议要求标记的重点内容，含原文位置，可直接跳转研读。

### 5.1 【重点】DO-178C 与国军标基线（p:108）

- **DO-178C** 按 DAL（设计保证等级）要求结构覆盖率，**A 级强制 MC/DC**，且**明确规定静态分析不能替代动态测试**——向合作方介绍系统能力时注意措辞边界。
- **GJB 8114-2013**（C/C++ 语言编程安全子集）：124 条强制性检查规则。
- **GJB 5369-2005**（航天型号软件 C 语言安全子集）：138 条规则。
- **两者构成国内军品嵌入式软件静态检测的事实基线** → 建议作为系统规则库对齐目标（对接加分项）。

### 5.2 【重点】大模型检测的严格评估要求（p:339, §2.5.3）

- **PrimeVul（ICSE 2025）**：严格去重、按时间划分与配对评估的 C/C++ 函数级基准（约 23 万函数、6,968 个漏洞函数、140+ CWE）。
- 严格设置下 SOTA 7B 模型 F1 从 Big-Vul 上的 68.26% **跌至 3.09%**，GPT 级模型接近随机猜测。
- **金句对应**："对于任何的 IR 检测能力，必须在严格去重和时间划分的基准上报告结果，否则结论不可信"——**我方任何检测指标汇报都要按此基准设定**，避免在对接中被质疑数据可信度。

### 5.3 【重点】通用工具在嵌入式场景"水土不服"的八项原因（p:344–351）

| # | 原因 | 核心内容 | 对我方系统的优化指向 |
|---|------|----------|---------------------|
| 1 | 编译器方言与内联汇编 | `__attribute__((interrupt))`、`#pragma location`、内联汇编导致解析偏差，轻则误报重则整文件跳过 | 前端需支持编译器扩展语法 |
| 2 | 内存映射寄存器与 volatile | 通用工具视为普通指针；只读寄存器被写、位域越界检查缺失；volatile "冗余读写"成为高频误报 | **寄存器读写合法性检查（P2）——本系统已有基础，是差异化卖点** |
| 3 | ISR 与主循环的并发 | 竞争关系由中断优先级与 RTOS API 语义决定，pthread 模型系统性漏报 | **中断优先级感知的数据竞争检测** |
| 4 | 无标准库与裸机启动代码 | "main 为入口、库函数语义已知"假设失效 | 裸机入口建模（Reset_Handler 等） |
| 5 | 交叉编译构建环境缺失 | CodeQL/Coverity/Clang 系均需构建数据库，IAR/make 工程导入即失败（P1，工业落地第一道门槛） | 免构建导入能力 |
| 6 | 第三方 SDK 闭源 | 过程间分析在库边界中断，调用链不完整 | 库边界的摘要建模 |
| 7 | RTOS 语义不可见 | 任务/队列/信号量 API 对分析器只是普通函数调用；死锁、优先级反转不可见（P2） | RTOS API 语义库（FreeRTOS/RT-Thread） |
| 8 | 性能与增量分析 | 全程序深度分析单次数小时，无法嵌入每日集成 | 基于调用图影响集的增量分析 |

### 5.4 【重点】本系统量化目标（p:141）——对接演示口径

1. 检测能力较单一基线（Cppcheck、Clang Static Analyzer）提升 **≥20%**；
2. LLM 智能体误报过滤使人工审查工作量下降 **≥30%**，且漏判率不高于基线；
3. 对 **MISRA C:2012 与 GJB 8114** 规则的覆盖（详见 p:141 原文）。

### 5.5 其他关键标注点

- **p:238**：Polyspace 类工具解决汽车 ISO 26262 / 航空 DO-178C 的运行时错误证明与合规，提供工具鉴定套件。

## 七、硬件语义专题调研（系统优化参考）

> 对应会议要求："通过调研获取硬件冗余、寄存器地址、中断处理等相关参考信息，为后续系统优化提供启发。"

### 7.1 寄存器地址与内存映射：机器可读资源（可直接做规则底座）

**核心资源是 CMSIS-SVD**：ARM 制定的 XML 标准，完整描述每个外设的基址、寄存器偏移/位宽/**访问权限（read-only / write-only / read-write）**、复位值、位域定义——正是"寄存器读写合法性检查"需要的全部语义，**无需人工整理寄存器手册**。

| 资源 | Stars | 说明 |
|------|-------|------|
| [modm-io/cmsis-svd-stm32](https://github.com/modm-io/cmsis-svd-stm32) | 259 | **全部 STM32 型号的 SVD 文件**——飞控/雷达样本基本都是 STM32，直接可用 |
| [cmsis-svd/cmsis-svd](https://github.com/cmsis-svd/cmsis-svd) | 1,211 | SVD 的 Python 解析库，可直接接入规则引擎 |
| [cmsis-svd/cmsis-svd-data](https://github.com/cmsis-svd/cmsis-svd-data) | 114 | 聚合的 ARM Cortex-M 全系 SVD 数据 |
| [rust-embedded/svd2rust](https://github.com/rust-embedded/svd2rust) | 865 | 证明"SVD → 类型化寄存器映射"自动转换路线成熟，可参照做 SVD → 检测规则 |
| [antoniovazquezblanco/GhidraSVD](https://github.com/antoniovazquezblanco/GhidraSVD) | 55 | SVD 导入 Ghidra，说明二进制固件场景也能复用同一套 SVD |

**落地路线**：解析目标芯片 SVD → 构建寄存器知识库（地址、访问权限、复位值、位域）→ 生成规则：①只读寄存器被写；②写保留位/保留寄存器；③位域赋值越界；④寄存器写序列违规（如 unlock 序列）。这套是相对 §5.3 原因 2（外设建模缺失）的直接解法，也是与通用工具拉开差距的差异化能力。

### 7.2 中断处理语义（可编码为检测规则）

嵌入式的并发单位是 **ISR 与主循环/RTOS 任务**，竞争关系由 **NVIC 中断优先级**决定（对应 §5.3 原因 3）。可从以下公开语义中提炼规则：

1. **volatile 共享**：ISR 与主循环共享的变量必须 volatile，否则编译器可能把主循环读取优化进寄存器（死等标志位类 bug 的根源）。
2. **FreeRTOS FromISR 规则**（官方文档明确）：ISR 中只能调用 `xxxFromISR` 变体 API；且只有优先级数值不低于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断才允许调用 RTOS API——违反即产生难复现的竞态，通用工具完全不可见。
3. **临界区成对性**：共享资源访问需 `__disable_irq()`/`taskENTER_CRITICAL()` 与恢复操作成对出现，且临界区内不得调用阻塞 API。
4. **ISR 内禁用操作**：阻塞延时、（多数平台的）动态内存分配、printf/日志等。

**学术对标（重点，可直接进论文相关工作）**：
- [PASAN（USENIX Security 2021）](https://www.usenix.org/system/files/sec21-kim.pdf)：**首个**静态检测裸机嵌入式外设访问并发 bug 的工具，核心思路正是**用中断优先级排序 ISR 与主循环的可达性竞争**，在三个平台发现 17 个真实并发 bug（检出率 40%–100%）。未找到开源实现——**我方若开源同类能力即为差异化**。
- ASE 2021 同方向：*"An Empirical Study on Concurrency Bugs in Interrupt-Driven Embedded Software"*、*"Automatic Detection, Validation, and Repair of Race Conditions in Interrupt-Driven Embedded Software"*（含自动修复，与我方一键修复闭环可对标）。
- 中断/并发论文检索索引：[wcventure/Concurrency-Paper-Info](https://wcventure.github.io/ConcurrencyPaper)。

### 7.3 硬件冗余：开源现状印证 + 文档级参考

- **GitHub 上 TMR/lockstep 的开源实现极少且均为课程级**（如 [d-graz/TMRonFreeRTOS](https://github.com/d-graz/TMRonFreeRTOS)、两三例 ESP32/Arduino 投票实验，均 ≤1★）——**印证了会议"已嵌入的开源硬件冗余相关代码行业有局限"的判断**：真实的冗余语义以芯片设计/文档形态存在，不以代码库形态存在。
- **文档级冗余语义参考**（可作为规则建模的语义来源）：
  - **Xilinx Zynq UltraScale+ RPU lockstep 模式**：双核锁步比对，航天/雷达常用平台，AMD 文档公开；
  - **Infineon AURIX TriCore lockstep**：汽车域控主流锁步 MCU（对标汽车类样本）；
  - **SpaceWire + RMAP 总线**（卫星标准总线）：开源实现 [yuasatakayuki/SpaceWireRMAPLibrary](https://github.com/yuasatakayuki/SpaceWireRMAPLibrary)（C++，33★）及 SpaceWire IP 核若干（VHDL）；
  - 常规手段：窗口看门狗、ECC、CRC 校验、N 版本程序设计 + 2-of-3 投票。
- **对检测规则的启发**：既然冗余以"设计模式"存在，规则应针对**冗余模式的实现错误**——投票器分支覆盖不全、TMR 状态变量被单点写（无冗余存储）、喂狗放在 ISR 里不可靠、锁步核间数据未同步等。

### 7.4 雷达场景硬件语义要点

- 雷达嵌入式代码的动态行为同时受**硬件系统约束和系统语义双重限制**（会议结论）：典型链路为 定时器触发 → ADC 采样 → DMA 搬运 → FFT/CFAR 处理，检测重点在**采样/DMA 缓冲区竞态、chirp 时序寄存器配置、中断与处理任务的同步**。
- TI IWR6843 类毫米波雷达的固件由 TI **闭源**提供，开源侧主要是 host 驱动——静态检测样本建议聚焦 **STM32 + 雷达前端**（如 §2.5 的 Sense2GoL 项目），而非芯片原厂固件。

### 8.2 逐项拆解："它是怎么做的"

**① CodeChecker（Ericsson）——工程管理闭环的开源标杆**
做法：封装 Clang Static Analyzer / Cppcheck 等引擎 → 分析结果（plist）进缺陷数据库 → Web 界面做去重、审阅、标记误报 → CI 门禁。**它本身不做分析，做的是告警生命周期管理**——和我们告警中心的"采纳/拒绝/修复提交"闭环同构。启示：它的分析器可插拔，我们系统未来可以把 Clang/Cppcheck 结果也接进来做融合分诊。

**② Fuzzware（USENIX Sec'22）——把寄存器语义"学"出来（动态路线）**
做法：Unicorn 模拟 Cortex-M 固件 + AFL++ 模糊测试；**MMIO 寄存器访问的值由 fuzzing 输入供给**，再对每次 MMIO 访问做符号执行，自动判断"这个访问是否影响固件逻辑"，把大多数状态轮询类访问自动消除/压缩成外设模型配置，pipeline 循环迭代：模拟 → 发现新 MMIO → 建模 → 更新配置 → 继续模拟。启示：**寄存器语义可以自动学习而非人工整理**；但它只能覆盖动态可达路径，且需要可运行镜像——静态检测侧仍需要 SVD 知识库（§7.1）补位。

**③ P2IM / DICE / AIM（同一团队）——外设接口三件套**
做法：在 QEMU 里把"处理器-外设接口"（寄存器+中断）自动建模，把寄存器按**语义角色分类**（配置/状态/数据/输入）；DICE 专攻 DMA 输入通道；AIM 专攻**中断接口建模**（覆盖异步逻辑提升 11.2 倍）。启示：**寄存器按语义角色分类的分类法**可直接搬进静态检测的寄存器知识库设计——比如"配置寄存器允许写一次""状态寄存器只读轮询"这类访问模式约束。

**④ FirmXRay（CCS'20）——静态路线处理裸机的样板**
做法：Ghidra 基座，三步：基址自动推断（指针指向关系启发式）→ **从 SDK API 调用点出发做反向切片**（不依赖 main 入口）→ 静态执行 ARM 指令求出配置值，从而检测 BLE 链路层配置漏洞。启示：**嵌入式代码没有标准入口时，SDK/RTOS API 是天然的语义锚点**——这直接回应八项水土不服的原因 4（无 main 假设失效）和 6（SDK 闭源）：把厂商 SDK 的 API 语义表建出来，就能在闭源库边界外恢复调用链语义。

**⑤ ESBMC + esbmc-ai——"验证器驱动 LLM 修复"闭环（已商业化）**
做法：ESBMC（SMT 模型检查）输出反例 → esbmc-ai 把技术性反例交给 LLM 生成修复 → 再回到 ESBMC 回归验证，插件化平台。**注意：esbmc-ai 已归档，后继为商用产品 Entoli**——说明"检测+LLM修复+验证闭环"有商业价值，我们的一键修复闭环走在同一条已被验证的路线上，差异点是嵌入式场景与硬件语义。

**⑥ Goblint / Karonte——两个反例教训**
Goblint 是 SV-COMP 并发冠军，但并发模型建立在 pthread 上，ISR/RTOS 场景系统性漏报（docx p:346 已引）——**通用并发引擎≠嵌入式可用**。Karonte（S&P'20，多二进制固件数据流分析）2021 年停更——**纯学术开源工具的维护断档**，也说明"规则库+LLM 降低维护成本"路线的合理性。

### 8.3 共性技术手法总结（可直接借鉴）

1. **硬件语义的三种获取方式**：(a) 机器可读规范（SVD，静态）；(b) 符号执行从访问模式学习 MMIO 模型（Fuzzware/P2IM，动态）；(c) SDK API 锚点+反向切片+静态值求值（FirmXRay，静态）。三者可组合：SVD 定底座，FirmXRay 式切片定上下文，访问模式学习补 SVD 缺失。
2. **寄存器语义角色分类法**（config/status/data/input）是经过顶会验证的知识库组织方式。
3. **中断语义的开源空白**：动态侧有 AIM（中断建模），静态侧 PASAN 闭源——**静态中断优先级感知并发检测至今无成型开源实现，是我方差异化空间**。
4. **LLM+验证器闭环已被验证可行并商业化**（Entoli），我们的先发点在嵌入式硬件语义。
