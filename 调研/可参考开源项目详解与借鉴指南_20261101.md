## 〇、总览与阅读优先级

| 优先级 | 项目 | 一句话定位 | 借鉴的核心 |
|--------|------|-----------|-----------|

| ★★☆ | Fuzzware | 寄存器语义自动学习（动态） | MMIO 访问模式自动分类，降规则编写量 |

## 一、FirmXRay（★★★）—— 静态硬件语义分析的直接模板

### 1.1 基本信息

- 仓库：https://github.com/OSUSecLab/FirmXRay（Java，78★，2020-09 创建，2024-10 后基本停更）
- 论文：*FirmXRay: Detecting Bluetooth Link Layer Vulnerabilities From Bare-Metal Firmware*，**CCS 2020**，OSU 安全实验室
- 依赖：仅一个 Ghidra 编译出的 jar；输入是**裸机固件二进制**（.bin），支持 Nordic SoftDevice 与 TI BLE-Stack 两种 SDK 的固件

### 1.2 它是怎么做的（三步流水线）

```
固件二进制(.bin)
   │
   ▼
① 基址自动推断 ── 用"指针指向关系"启发式从二进制反推固件加载基址
   │              （裸机镜像没有 ELF 头，地址全靠猜，这一步解决分析起点问题）
   ▼
② 反向切片 ────── 以 SDK API 调用点为锚点（如 sd_ble_gap_sec_params_reply），
   │              从调用点反向提取所有影响该调用的程序路径
   │              ★ 关键：不依赖 main 入口、不要求全程序分析
   ▼
③ 静态值求值 ──── 对切片内的 ARM 指令做静态执行，算出传给 API 的配置实参
   │              （如 sec_params=205），再对照协议规范判定配置漏洞
   ▼
输出 JSON：每个 API 调用点的已求解配置值 + 漏洞判定
```

实测数据（README 示例）：4.4KB 固件、5 条程序路径、12.7 秒完成分析。

### 1.3 我们具体参考哪里

| 借鉴点 | 对应我们系统的问题 | 具体做法 |
|--------|-------------------|----------|
| **SDK API 锚点分析** | 八项水土不服之④（裸机无 main 假设失效）、⑥（SDK 闭源断链） | 不从 main 出发做全程序分析，改为**从 HAL/RTOS API 调用点反向切片**。为常用 SDK（STM32 HAL、FreeRTOS）建 API 语义表，调用点即语义锚点——闭源库本体不需要分析 |
| **静态值求值** | 寄存器配置类检测（时钟配置错误、波特率算错） | 对 LLVM IR 做切片内常量传播/区间求值，算出写入寄存器的配置值，对照 SVD 中的合法值域检查——比通用"位域越界"规则精准得多 |
| **Ghidra 模式的知识注入** | 检测规则与硬件知识分离 | 它把 Nordic/TI SDK 知识（API 语义）做成独立知识层，分析引擎可换 SDK 复用。我们同样应把 STM32/雷达前端 SDK 语义做成可插拔知识包 |

### 1.4 不适用部分 & 上手建议

- 不适用：它面向二进制，我们走源码/LLVM IR——只搬**方法论**，不搬代码。
- 上手：先读论文第 4 节（设计），再看 `src/` 下三个主组件约 2~3 千行 Java，重点看切片和值求值的实现顺序。

## 二、P2IM / DICE / AIM（★★★）—— 寄存器知识库的组织范式

### 2.1 基本信息

- 仓库：https://github.com/RiS3-Lab/p2im（C/Python，149★）+ [DICE-DMA-Emulation](https://github.com/RiS3-Lab/DICE-DMA-Emulation)（S&P'21）+ [AIM-Interrupt-Modeling](https://github.com/bofeng17/AIM-Interrupt-Modeling)（TDSC'23）
- 论文：P²IM（USENIX Security'20）、DICE（IEEE S&P'21）、AIM（IEEE TDSC 2023），UC Riverside RiS3-Lab
- 全部基于 QEMU，AFL 集成用 TriforceAFL

### 2.2 它是怎么做的

**P²IM（外设寄存器建模）**：QEMU 只支持少数开发板的外设，真实固件一访问未实现寄存器就跑不动。P²IM 在 QEMU 里对 MMIO 访问做**在线符号执行**，把每个寄存器自动归类为四种语义角色，并按角色注入不同行为：

| 角色 | 固件典型用法 | P²IM 注入的模型行为 |
|------|-------------|-------------------|
| **Config（配置）** | 初始化时写一次 | 写入即接受，值不影响控制流 |
| **Status（状态）** | 循环轮询读 | 按策略翻转就绪位，推动控制流前进 |
| **Control/Data（控制/数据）** | 触发动作/收发数据 | 有条件地返回数据、改变状态 |
| **Input（输入）** | 外部世界的数据来源 | 由 fuzzing 输入填充 |

**DICE**：同一方法论处理 DMA——自动识别 DMA 输入通道并建模，解决"外设直接往内存写数据"的场景。
**AIM**：专攻**中断接口**——此前工作全部忽略中断，AIM 自动建模"何时该触发哪个中断"，使异步（中断驱动）逻辑覆盖率提升最高 **11.2 倍**。实现基于 angr + 动态符号执行。

### 2.3 我们具体参考哪里

| 借鉴点 | 对应我们系统的问题 | 具体做法 |
|--------|-------------------|----------|
| **寄存器语义角色分类法**（最重要） | 寄存器知识库如何组织（§7.1 的 SVD 只有物理属性，没有语义角色） | SVD 解析出的每个寄存器再打上 config/status/data/input 标签，**每类挂不同检测规则**：config 类查"重复配置/配置值越界"、status 类查"写了只读状态位"、data 类查"缓冲区边界"、input 类查"未做输入校验"。分类可先按访问模式启发式（见 Fuzzware 条目），人工只审核边界样本 |
| **中断建模的优先级意识** | ISR 并发检测（八项之③） | AIM 的核心观察：中断是"外部异步输入源"，检测时要枚举"任意时刻任意允许的中断可打断任意任务"。我们把 NVIC 优先级表当作输入（SVD/CMSIS 头文件里有），按优先级推导"哪些 ISR 对能构成真竞争"——PASAN 未开源，这条是唯一公开的方法参照 |
| **寄存器行为 ≠ 指针读写** | volatile 高频误报（八项之②） | P²IM 证明寄存器访问必须按语义解释而非按内存语义解释。我们的规则引擎对指向 MMIO 地址段的指针解引用要走"寄存器访问"分支而不是"内存访问"分支，从根上消掉"冗余读写"误报 |

### 2.4 不适用部分 & 上手建议

- 不适用：QEMU/符号执行整条动态链路我们不搬；p2im 主仓库 2023-10 后停更，代码当文献读。
- 上手：三篇论文都读不现实，**只精读 P²IM 论文第 5 节（模型实例化）和 AIM 论文的中断建模章节**；代码看 `model_instantiation/` 目录里寄存器分类器的特征定义即可。

## 三、esbmc-ai + ESBMC（★★★）—— 修复闭环的唯一开源对标

### 3.1 基本信息

- 仓库：https://github.com/esbmc/esbmc（C++，536★，**今天仍在提交**）、https://github.com/esbmc/esbmc-ai（Python，43★，**已归档**）
- ESBMC：*Efficient SMT-based Context-Bounded Model Checker*，支持 C/C++/嵌入式约定，k-归纳证明，SV-COMP 多届获奖
- esbmc-ai：2023-04 启动，插件化 LLM 工作流平台；**官方声明已停止开发，后继为商用产品 Entoli（byterepair.io）**

### 3.2 它是怎么做的

```
ESBMC 模型检查
   │  输出：技术性反例（violated property + 变量轨迹 + 反例路径）
   ▼
esbmc-ai 编排层（插件化）
   │  ① 把 ESBMC 技术输出"翻译"成 LLM 可理解的修复任务描述
   │  ② LLM 生成补丁
   │  ③ 回到 ESBMC 重新验证补丁 —— 不通过则带反馈重试
   ▼
验证通过的修复 + 证据链
```

关键工程决策：**LLM 只做生成，不做判定**；判定权始终在形式验证器手里。平台通过 Addon 机制扩展命令，支持 Docker 分发。

### 3.3 我们具体参考哪里

| 借鉴点 | 对应我们系统的问题 | 具体做法 |
|--------|-------------------|----------|
| **"翻译层"设计** | 我们 LLM 修复的输入是什么？ | 它专门做了一层"反例→修复任务"的转换（README 明说 ESBMC 输出太技术性）。我们给 LLM 的输入也不该是原始告警 JSON，而是结构化的：缺陷模式 + 相关代码切片 + 触发条件 + 硬件语义上下文 |
| **验证回归闭环** | 自动修复如何避免"改坏了" | 修复必须过原检测器复检。我们的一键修复已有验证环节，可对照它补：**修复失败时把失败原因喂回 LLM 的重试机制**（它有，我们若有需确认） |
| **插件化命令平台** | 系统扩展性 | Addon 式扩展让新检测器/新修复策略即插即用；我们后续接 GJB 规则包、雷达场景包时可参照 |
| **商业化信号** | 方向判断 | 转商用 Entoli 说明该闭环有市场——我们演示时的"为什么这么做"有了行业佐证 |

### 3.4 不适用部分 & 上手建议

- 不适用：ESBMC 的 SMT 求解本身（当前阶段），k-归纳证明在无构建环境的嵌入式工程上难以落地。
- 上手：esbmc-ai 代码是 Python，直接读 `esbmc_ai/` 下 orchestrator 与 repair 命令实现；仓库已归档，不会有更新，读快照即可。ESBMC 留作远期"修复后验证器"选项。

## 四、Fuzzware（★★☆）—— 寄存器语义自动学习（降规则编写量）

### 4.1 基本信息

- 仓库：https://github.com/fuzzware-fuzzer/fuzzware（Python+C，390★，2022-01 创建，2026-06 后边缘维护）
- 论文：USENIX Security'22（PDF 在 README 顶部）；子仓库：fuzzware-emulator（Unicorn 模拟）、fuzzware-pipeline（编排）、/modeling（MMIO 建模，基于 angr）

### 4.2 它是怎么做的

```
固件镜像 + 内存映射配置 → Unicorn 模拟执行 + AFL++ 模糊测试
        │
        │  MMIO 访问发生 → 值从 fuzzing 输入供给（fuzzer 猜硬件行为）
        ▼
建模组件对每次 MMIO 访问做符号执行，回答一个问题：
"固件如何使用这个读到的值？"
        │
        ├─ 值不影响控制流（状态轮询/握手）→ 自动消除或压缩成简单模型
        └─ 值影响控制流 → 建模为需 fuzzing 供给的输入点
        ▼
新模型配置回灌模拟器 → 覆盖率继续推进 → 循环迭代
```

核心洞察：**固件对 MMIO 的大量访问是"输入无关"的**（读状态位死等、清中断标志），这些访问可自动识别并消除，真正需要建模的寄存器只是少数。

### 4.3 我们具体参考哪里

| 借鉴点 | 对应我们系统的问题 | 具体做法 |
|--------|-------------------|----------|
| **MMIO 访问模式自动分类** | 寄存器规则编写量太大（一块 STM32 芯片上千个寄存器） | 静态版移植：在 LLVM IR 上统计每个寄存器地址的**读写序列模式**（只读/读后写/固定写序列/写后不读），自动打上 P²IM 式语义角色初标 + 生成"该寄存器无副作用"白名单——规则编写只聚焦少数影响控制流的寄存器 |
| **配置文件化模型** | 知识库形态 | 它的硬件模型是 YAML 配置（README_config.yml），引擎与知识分离。我们的寄存器知识库同样做成数据文件（SVD+角色+约束），检测引擎通用 |
| **"boot 成功状态"判定** | 测试样本预筛 | 它自动识别成功启动的固件状态。我们筛测试样本时同理：能在模拟环境跑过启动代码的样本才进入检测集 |

### 4.4 不适用部分 & 上手建议

- 不适用：动态 fuzzing 全链路；Unicorn 模拟与我们的静态 IR 分析不在一条路线上。
- 上手：读论文 Section 4（MMIO modeling）；代码看 `/modeling` 里访问分类的特征提取函数，把"值是否影响控制流"的判据翻译成 IR 上的 use-def 分析即可。

## 五、CodeChecker（★★☆）—— 生产级工程化标杆

### 5.1 基本信息

- 仓库：https://github.com/Ericsson/codechecker（Python，2,631★，2015-06 创建，**持续活跃 11 年**，上次提交 2026-10-29）
- 出处：Ericsson，基于 LLVM/Clang 工具链，定位是替代 scan-build 的静态分析基础设施

### 5.2 它是怎么做的

**命令行侧**：
- `CodeChecker log -b "make"` **旁路截获任意构建过程**生成 JSON 编译数据库；
- **自动分析 GCC 交叉编译工程**：探测 GCC/Clang 编译配置，自动变换成 clang 分析器调用；
- 集成 Clang SA（含跨翻译单元分析）、Clang-Tidy、Cppcheck、GCC Static Analyzer、Facebook Infer 多引擎；
- **增量分析**：只重析变更文件及其依赖。

**服务端侧**：
- 报告入库（PostgreSQL/SQLite），Web 界面支持按 checker/严重级/路径过滤；
- **Diff 模式**：两次分析对比，标出"新引入/已修复"的告警（即版本间告警差分——我们 1.2.0 刚做了类似功能，可对照补全）；
- 误报抑制带评审注释；GitLab/Gerrit 评审集成。

### 5.3 我们具体参考哪里

| 借鉴点 | 对应我们系统的问题 | 具体做法 |
|--------|-------------------|----------|
| **交叉编译工程适配**（最值钱） | 八项之⑤（构建环境缺失，工业落地第一道门槛） | 我们不要求跑通用户构建，但可以抄它的"旁路截获+编译配置探测"思路：从 make/CMake/IAR 工程文件**解析出宏定义、include 路径、目标架构**喂给 clang/我们的前端——不需要真编译，只需要编译配置 |
| **增量分析** | 八项之⑧（深度分析进不了 CI） | 以文件+依赖图为单位做增量调度；全量深度分析只跑变更影响集 |
| **告警 diff 与审阅流** | 告警中心功能对齐 | 对照补全：跨版本 diff 报告（新增/消失/仍在）、误报抑制的持久化与评审注释、多引擎结果统一入库 |
| **多引擎结果归一** | 融合分诊 | 它把 5+ 个分析器的异构结果归一成统一报告模型——我们融合 Clang/Cppcheck/自有规则结果时可参考其数据模型 |

### 5.4 不适用部分 & 上手建议

- 不适用：分析引擎本身（Clang 系通用引擎的嵌入式短板 docx 已论证）；OCaml/Web 技术栈不必照搬。
- 上手：不用读代码，先跑一遍 demo（README 有在线 demo），重点体验 log → analyze → web → diff 的工程流；文档在 codechecker.readthedocs.io。

## 六、Goblint（★☆☆）—— 只借框架，避开模型

### 6.1 基本信息

- 仓库：https://github.com/goblint/analyzer（OCaml，254★，2011-07 创建，**今天仍在提交**，活跃 15 年）
- 论文：SV-COMP 并发赛道常胜军；docx p:346 已引用其在 ISR 场景的系统性漏报

### 6.2 它是怎么做的

C 程序抽象解释框架：基于 Cylinder/格 的抽象域组合，**协程感知（thread-modular）不动点求解**——每个线程独立算不变量、通过共享变量的抽象域交换信息，避免全局状态爆炸。支持 pthread、互斥锁、各种内存模型精化。

### 6.3 我们具体参考哪里

| 借鉴点 | 说明 |
|--------|------|
| thread-modular 不动点框架 | 做 ISR 并发分析时的算法骨架：把 ISR 与主循环当"协程"，共享 volatile 变量做信息交换点——**框架可搬，模型必须换**（pthread 锁语义 → NVIC 优先级语义） |
| 抽象域组合的工程组织 | 它的抽象域可插拔组合（区间+位域+锁集……），我们做寄存器值域分析时可借鉴 |

### 6.4 不适用部分

pthread/锁的并发模型整体不可搬——这正是 docx 论证的通用工具系统性漏报根源，也是我们要自己造的部分（PASAN 未开源，此为空白）。

## 七、ESBMC 本体（★☆☆）—— 远期验证器选项

- 仓库：https://github.com/esbmc/esbmc（C++，536★，活跃）；支持 C/C++、断言/越界/溢出性质检查、k-归纳
- 参考价值：当前阶段只作为 esbmc-ai 的上游理解；**远期若要给自动修复加形式化"复核器"**（比 LLM 复检更强的保证），ESBMC 是现成开源选项。注意它同样需要可构建的工程，嵌入式落地受八项之⑤制约——这也是它没成为我们主引擎的原因。

## 八、借鉴整合：落到我们系统的四步路线

```
第 1 步：寄存器知识库（P²IM 分类法 × SVD × Fuzzware 模式学习）
  SVD 解析（§7.1 资源）→ 寄存器物理属性
  IR 访问模式统计（学 Fuzzware）→ config/status/data/input 自动初标（学 P²IM）
  产出：数据文件化的寄存器知识库 + 4 类访问合法性规则

第 2 步：分析入口改造（学 FirmXRay）
  无 main 假设 → SDK API（HAL/FreeRTOS）调用点作锚点，反向切片
  切片内静态值求值 → 寄存器配置值对照知识库检查

第 3 步：ISR 并发检测（AIM 思想 + NVIC 优先级，避 Goblint 模型）
  中断向量表 + 优先级表为输入
  ISR×主循环 volatile 共享变量 → 优先级推导真竞争
  （此方向无成型开源实现，为论文级差异化点）

第 4 步：工程化与修复闭环（学 CodeChecker + esbmc-ai）
  编译配置解析（make/CMake/IAR）→ 免构建导入
  增量分析 + 告警 diff + 修复失败反馈重试
```

**优先级依据**：第 1 步是差异化卖点（寄存器语义），第 3 步是学术空白（论文点），第 2 步决定样本能不能跑起来，第 4 步决定演示观感。若时间只够做一件事，做第 1 步。
