# 真实嵌入式开源测试项目集（详细版）

> 用途：嵌入式代码检测系统的真实测试对象。以下 12 个项目均为公开开源仓库，信息核实于 2026-11-01。每个项目介绍它是什么、用来干什么、里面包含什么内容，以及拿它测试检测系统时能验证什么。

**术语说明**（正文中反复出现，先统一解释）：

- **CWE**（Common Weakness Enumeration，通用缺陷编号体系）：国际通用的软件缺陷编号标准，每个编号对应一类缺陷，如 CWE-134 代表格式化字符串问题。
- **MISRA C**（汽车/铁路/航天领域通用的 C 语言安全编码规范）：行业内要求嵌入式软件遵守的编码规则集，违规即报警。
- **CERT C**（美国卡内基梅隆大学 CERT 安全编码规范）：另一套权威的 C 语言安全编码规则集。
- **FreeRTOS**（开源实时操作系统）：嵌入式设备上最常用的操作系统内核，负责任务调度和通信。
- **CAN**（Controller Area Network，控制器局域网）：汽车内部各电脑之间通信的总线；**CAN FD** 是它的增强版，带宽更大。
- **CubeSat / 立方星**：以标准单位（1U 约 10×10×10 厘米）拼装的廉价小卫星，高校和初创公司常用。
- **fuzzing**（模糊测试）：把随机的、畸形的输入数据大量灌进程序，看它会不会崩溃或出错，是自动化安全测试的主要手段。

## 1. NASA cFE（cFS 核心飞行执行层）

- **仓库**：https://github.com/nasa/cFE （整套体系汇总仓库：https://github.com/nasa/cFS ）
- **许可**：Apache-2.0（宽松许可，可自由使用）｜ **开源时间**：2017 年 ｜ **状态**：持续活跃更新
- **语言/规模**：C 语言，88,260 行，541 个源文件

### 是什么

NASA（美国国家航空航天局）戈达德中心研制的航天器飞行软件核心框架。它本身不控制任何具体设备，而是给所有航天应用软件"打地基"：负责应用的启动与监控、软件之间的消息传递、事件日志、在轨参数表管理、航天器时间管理。NASA 多个真实航天任务（包括国际空间站上的载荷）都在用它，是公开可得的、最权威的真实在轨飞行软件。

### 项目里有什么

整套软件按功能拆成十几个模块，各自职责：

- **ES（执行服务）**：管理所有应用的生命周期——注册、启动、重启、健康检查；
- **SB（软件总线）**：核心的消息快递系统，各应用之间通过"发布/订阅"传消息，互不直接调用；
- **TBL（表服务）**：管理在轨可上传修改的参数表，带双重缓冲和校验，改错了能回滚；
- **EVS（事件服务）**：统一的日志与告警上报通道；
- **TIME（时间服务）**：航天器统一时间源和时区换算；
- **MSG（消息格式）**：兼容国际通用的 CCSDS（空间数据系统咨询委员会）航天器消息标准；
- **FS（文件服务）**、**SBR（消息路由）**、**resourceid（资源编号管理）**等辅助模块；
- **cfe_assert + cfe_testcase**：NASA 官方自带的测试框架和 34 个功能测试用例——官方自己就把测试资产开源了。

`docs/` 目录里有完整的《cFE 应用开发指南》和功能需求对照表（CSV 格式），每个功能都能查到依据。

### 拿它测试检测系统时能验证什么

它是纯 C 写的真实航天软件，规模适中（8.8 万行）又有国际权威背书——演示说服力最强。我们已实测跑通：检出 14,094 条告警，其中高危 132 条集中在"格式化字符串不安全"问题（printf 这类输出函数的第一个参数如果用了变量拼接，可能被恶意利用，对应 CERT FIO30-C 规则 / CWE-134 编号）。另外它自带完整测试用例，动态测试（把软件真正跑起来灌输入）也不缺素材。

### 获取方式

已在本地 `projects/nasa-cfe/`。重新下载：`git clone --depth 1 https://github.com/nasa/cFE.git`

## 2. NASA F′（fprime）

- **仓库**：https://github.com/nasa/fprime
- **许可**：Apache-2.0 ｜ **开源时间**：2017 年 ｜ **状态**：持续活跃更新 ｜ GitHub 1.1 万星
- **语言**：C++ 为主，附自带建模语言 FPP

### 是什么

NASA 喷气推进实验室（JPL）研制的另一套飞行软件框架，最有名的实绩是**火星直升机 Ingenuity**——2021 年人类首次在另一颗行星上的动力飞行，它的飞控软件就是基于 F′ 构建的。与 cFE 的"C 语言分层架构"不同，F′ 采用组件化设计：软件拆成一个个独立组件，组件之间通过标准化的"端口"传数据，像积木一样拼装。

### 项目里有什么

- **Fw/**：基础库（基本类型、组件对象模型、命令与遥测的基础设施）；
- **Svc/**：核心服务组件（命令分发、遥测收集、事件上报、健康监测等现成积木）；
- **Os/**：操作系统抽象层（屏蔽 Linux/VxWorks 等底层差异）；
- **Drv/**：驱动组件（串口、SPI、I2C、网络等常见硬件接口）；
- **CFDP/**：CCSDS 文件传输协议实现（航天器与地面之间传文件的标准协议）；
- **Fpp/**：F′ 自家的建模语言及其编译器（用配置文件描述组件和接口，自动生成连接代码）；
- **STest/、FppTestProject/**：随机测试框架和建模语言的测试工程。

### 拿它测试检测系统时能验证什么

它代表"组件化 + 代码自动生成"的现代航天软件形态，可以验证检测系统对 C++ 工程、以及对"手写代码 + 自动生成代码"混合项目的适应能力。自带参考应用和地面测试系统，在 Linux 上能直接编译运行，动态测试条件好。

## 3. betaflight

- **仓库**：https://github.com/betaflight/betaflight
- **许可**：GPL-3.0（传染性开源协议：只作测试输入没问题，不能把它的代码并入闭源产品）｜ **开源时间**：2015 年 ｜ **状态**：持续活跃更新 ｜ GitHub 1.17 万星
- **语言/规模**：C 语言，体量数百万行级别

### 是什么

全球航模和无人机圈使用最广的开源飞控固件之一。装机量大、迭代快，代码直接操作单片机最底层的寄存器——**是所有候选项目里"硬件相关代码"密度最高的**。

### 项目里有什么

源码按功能分成 18 个目录，主要的：

- **drivers/**：STM32（意法半导体最常用的单片机系列）各外设的底层驱动——SPI、I2C、UART 串口、DMA（不经 CPU 直接搬运数据的通道）、定时器，以及几十种传感器芯片的驱动；
- **fc/**：飞控主调度（初始化流程、主循环）；
- **flight/**：飞行算法（姿态解算、PID 控制器、导航）；
- **sensors/**：陀螺仪、加速度计、气压计、罗盘等传感器的统一抽象；
- **rx/**：各种遥控接收协议的解析；
- **osd/**、**msp/**、**cli/**：屏幕叠加显示、调试协议、命令行配置；
- **target/**：几十种不同硬件板的引脚和配置定义。

### 拿它测试检测系统时能验证什么

飞控的实时性代码全是"中断程序和主循环共享数据"的结构，正是通用检测工具（面向普通电脑软件设计）最容易漏报误报的场景——拿它检验我方硬件语义类检测能力的差异化价值最合适。测试时建议只截取 drivers 子目录（全量太大）。它自带可在电脑上运行的单元测试（不需要无人机硬件就能跑算法层测试），但没有"软件在环"仿真（即没有官方的电脑仿真整机运行方案），驱动层动态测试需要仿真器或真硬件。

## 4. satellogic/canopus

- **仓库**：https://github.com/satellogic/canopus
- **许可**：GPL-3.0 ｜ **开源时间**：2013 年（本清单最早的航天软件仓库）｜ 2016 年后停止维护（作为"历史在轨代码"样本恰好合适）
- **语言/规模**：C 语言，约 2.9MB

### 是什么

阿根廷卫星公司 Satellogic 前身做的 CubeBug 系列立方星的飞行计算机软件，CubeBug-1 和 CubeBug-2 两颗星分别在 2013、2014 年真实发射入轨。这里发布的版本是两颗星之间重构后的版本，README 明确说明是真实飞行软件。

### 项目里有什么

README 给出的核心设计：Canopus 是一套**基于"channel（通道）"概念的硬件抽象层**（屏蔽具体硬件差异的中间层）——上层功能代码通过统一的"通道"和设备打交道，不管设备是真实硬件还是仿真器。真实飞行计算机运行在 **TI TMS570 芯片 + FreeRTOS** 上：TMS570 是德州仪器出品的双核互检安全芯片（两个相同的处理器核心跑同样的程序、实时比对结果，发现不一致立刻报警，是汽车和航天功能安全领域的主流方案）。同一套上层代码还能通过 FreeRTOS 的 PC 移植版在 **Linux 上直接构建运行**（项目里就有 linux32/linux64 两个工程）。

目录：`src/lib/canopus`（核心抽象层，README 原话"所有精华代码都在这里"）、`src/apps`（上层应用）、`src/boards`（板级适配）、`src/kernel`（内核适配）、`projects/`（三个目标平台的工程）。

### 拿它测试检测系统时能验证什么

一是真实在轨代码的权威性；二是它用 FreeRTOS，正好检验我方对 RTOS（实时操作系统）类接口误用的检测（例如中断程序里调了不该调的接口）；三是同一套代码能在 PC 上跑，意味着不用卫星硬件就能做动态测试——是所有真实航天代码里动态测试门槛最低的。

## 5. OpenCyphal/libcanard

- **仓库**：https://github.com/OpenCyphal/libcanard
- **许可**：MIT（宽松许可）｜ **开源时间**：2015 年 ｜ **状态**：持续活跃更新 ｜ GitHub 451 星
- **语言/规模**：C 语言，约 0.6MB（小而精）

### 是什么

Cyphal（原名 UAVCAN，无人机和航天器使用的开放总线协议）的 CAN 传输层 C 语言实现，官方定位"高完整性实时系统"，支持协议的多个版本、经典 CAN 与 CAN FD、以及双总线冗余配置（一条总线坏了另一条顶上），兼容 8 位到 64 位的各种单片机。

### 项目里有什么

- `libcanard/`：协议核心——CAN 帧的编码解码、发送队列管理、接收消息分发、字节序转换；
- `lib/`：辅助库（可变长度整数编码等）；
- `tests/`：单元测试；`demos/`：示例程序；CI 持续集成 + 覆盖率统计齐全。

### 拿它测试检测系统时能验证什么

协议解析类代码的特征是大量指针运算和字节数组操作，是缓冲区越界类缺陷（CWE-125 读越界 / CWE-787 写越界）的高发区。它体量小、零硬件依赖、可直接编译——最适合拿来做模糊测试（把伪造的 CAN 帧数据灌进接收函数看会不会崩），是规则引擎精读和动态 fuzzing 两头都能用的基准样本。

## 6. driftregion/iso14229

- **仓库**：https://github.com/driftregion/iso14229
- **许可**：MIT ｜ **开源时间**：2021 年 ｜ **状态**：持续活跃更新 ｜ GitHub 373 星
- **语言/规模**：C 语言，约 0.7MB

### 是什么

ISO 14229（UDS，Unified Diagnostic Services，汽车统一诊断服务协议）的开源实现库。汽车修车和刷程序用的诊断仪，跟车内电脑对话用的就是这个协议——这是汽车行业最核心的标准协议之一。工程化程度很高：README 上挂着持续集成、覆盖率统计，以及 **Coverity Scan 徽章**（Coverity 是行业头部商业静态检测工具，意味着这个项目持续被商业工具扫过，可以直接拿来跟我们的结果对比）。

### 项目里有什么

- 整个库只有 **两个文件**（iso14229.c / iso14229.h），拿走就能用；
- 支持 ISO-TP（ISO 15765-2，CAN 总线上的数据分包传输协议）传输层；
- **纯静态内存分配**（完全不用 malloc 动态内存，嵌入式安全编码的推荐做法）；
- **MISRA 偏差有专门文档 docs/MISRA.md**（哪些编码规范条款它故意不遵守、为什么，都写在文档里）；
- 示例覆盖 ESP32、Arduino、NXP S32K144（车规级芯片）、STM32、Zephyr 等主流平台；
- `src/`（UDS 协议状态机）、`platforms/`（平台适配层）、`examples/`、`test/`。

### 拿它测试检测系统时能验证什么

最有价值的一点：它有官方 MISRA 偏差文档——把我们的检测跑上去，凡是命中"文档里已声明故意违反的条款"的就是误报，可以**定量算出引擎误报率**，做检测工具横向对比。另外诊断协议的状态机（会话管理、安全解锁、固件传输）对畸形输入序列的抵抗能力，正好用模糊测试验证。

## 7. commaai/panda

- **仓库**：https://github.com/commaai/panda
- **许可**：MIT ｜ **开源时间**：2017 年 ｜ **状态**：持续活跃更新 ｜ GitHub 1,708 星
- **语言/规模**：C 语言约 4.6MB（固件本体）+ Python 上位机

### 是什么

美国公司 comma.ai 的车载 CAN/CAN FD 通信设备固件，跑在 STM32H725 芯片上。它不是实验品——随 openpilot 装在 300 多种车型的真实用户车上天天跑，**是量产在用的汽车安全相关固件**。

### 项目里有什么

- `board/`：固件本体——`board/stm32h7`（芯片驱动）、`board/drivers`（外设驱动）、`board/crypto`（硬件加密）、`board/sys`（系统底层）；
- `python/`：电脑端控制库；
- `tests/`：**safety 测试**（安全逻辑测试）——这个项目最有名的资产：以车速、刹车、按键等状态为输入，断言固件"什么情况下允许哪条 CAN 消息通过"，防止恶意指令到达车辆执行器；
- 车型安全规则由姊妹仓库 opendbc 按车型编译进固件（规则代码是按配置生成的）。

### 拿它测试检测系统时能验证什么

静态上：中断驱动的 CAN 收发、环形缓冲区、寄存器级驱动，是汽车类硬件检测的典型样本。动态上：`tests/safety` 是成熟可直接跑的汽车安全动态测试框架（纯 Python，不用接真车），可以作为我们动态检测能力的对照实验。它同时具备"汽车行业"和"硬件底层"两个属性——对接时如果需要汽车类项目佐证能力，首选它。

## 8. commaai/openpilot

- **仓库**：https://github.com/commaai/openpilot
- **许可**：MIT ｜ **开源时间**：2016 年 ｜ **状态**：极活跃（几乎每天都有提交）｜ GitHub 6.4 万星（本项目集最高）
- **语言**：Python 为主 + C++（消息序列化和日志组件）

### 是什么

支持 300 多种车型的开源驾驶辅助系统（ADAS，高级驾驶辅助），comma.ai 的主产品，开源自动驾驶领域知名度最高的项目。

### 项目里有什么

- `openpilot/`：驾驶辅助主逻辑（感知、规划、控制）；
- `system/`：系统级服务（GPS 解析、数据记录、界面）；
- `tools/`：数据回放、标定、仿真工具——自带基于 CARLA（开源驾驶仿真器）的整车仿真环境，可以在电脑里仿真跑完整套系统；
- C++ 部分集中在 cereal（自研高性能消息总线库）和日志组件。

### 拿它测试检测系统时能验证什么

定位是"超大规模真实工程"的演示对象：验证检测系统在大体量、多语言混合项目上的增量分析能力。规则调优不是用它（体量太大），动态演示可以借助它的仿真环境。

## 9. UBC-Rocket/FLARE

- **仓库**：https://github.com/UBC-Rocket/FLARE
- **许可**：GPL-3.0 ｜ **开源时间**：2018 年 ｜ 2025 年仍有提交 ｜ GitHub 19 星
- **语言/规模**：C++ 约 5.4MB

### 是什么

英属哥伦比亚大学（加拿大名校）火箭社的竞赛火箭航电固件，负责飞行数据记录和降落伞开伞控制——高校航天工程的代表性真实项目。

### 项目里有什么

- `avionics/`：航电主代码（传感器读取、飞行状态判断、开伞时序控制）；
- `options.h`：全部可调配置宏集中在此，其中 `TESTING`（调试输出开关）和 `GROUND_TEST`（地面点火测试开关）两个宏的注释原话是"烧录到飞行板时绝对不能定义"——调试用的开关如果误入了飞行版本的构建，飞行时行为会完全错误；
- `test/`、`data/`、`doc/`。

### 拿它测试检测系统时能验证什么

它暴露了一类真实事故来源：**配置宏用错**（调试开关忘关就上天）。这可以提炼成一条实用检测规则——构建配置里出现 TESTING/GROUND_TEST 这类调试宏即判高危。代码风格是典型的学生竞赛工程，防御性写法不一致，通用缺陷规则命中率高。

## 10. UWCubeSat/DubSat1

- **仓库**：https://github.com/UWCubeSat/DubSat1
- **许可**：仓库无许可声明（默认版权保留：只本地测试，不对外分发其代码）｜ **开源时间**：2017 年 ｜ 2022 年后停止维护
- **语言**：C

### 是什么

华盛顿大学立方星团队 DubSat-1（3U 立方星）的**全资产仓库**：不仅源码，连 PCB 电路图、结构设计文件都放在同一个库里。README 里有正式的分支管理规范（master 必须始终可用、开发走 feature 分支）——配置管理意识接近工业界的学生卫星项目，计划 2018 年夏发射。

### 项目里有什么

## 11. frisnit/STM32L476-radar

- **仓库**：https://github.com/frisnit/STM32L476-radar
- **许可**：仓库无许可声明（只本地测试）｜ **开源时间**：2015 年 ｜ 2016 年后停止维护 ｜ GitHub 45 星

### 是什么

用 STM32L476-Discovery 开发板（意法半导体的评估板）加一个多普勒运动传感器做的**测速雷达**：雷达波打向移动物体，接收反射波算频率差，换算出速度并显示。作者为它写了 RS 在线设计社区的技术博客和演示视频，在硬件爱好者圈子里流传较广。

### 项目里有什么

体量小，几分钟就能完整跑通一遍检测——**对接演示里"贵单位是雷达方向，我们拿雷达代码当场测"环节的现成素材**：链路结构（采集→处理→输出）与真实雷达产品同构，且采样和数据搬运部分正好能带出硬件相关的检测能力。

## 12. yuasatakayuki/SpaceWireRMAPLibrary

- **仓库**：https://github.com/yuasatakayuki/SpaceWireRMAPLibrary
- **许可**：见仓库说明 ｜ **开源时间**：2011 年（本清单最早的仓库）｜ 2021 年后停止维护 ｜ GitHub 33 星
- **语言**：C++

### 是什么

**SpaceWire 和 RMAP 协议**的开源 C++ 实现。SpaceWire 是欧洲航天局主导制定的航天器高速总线标准，广泛用于卫星内部设备互联；RMAP（Remote Memory Access Protocol，远程内存访问协议）跑在 SpaceWire 之上，是卫星里读写设备寄存器的标准方式。源自日本 JAXA 相关的工程生态——航天味最浓的总线协议代码。

### 项目里有什么

- `includes/` + `sources/`：SpaceWire 帧与 RMAP 包的编解码、CRC 校验（循环冗余校验，一种数据完整性校验算法）、协议状态机；
- `test/`：自带测试；`exampleMakefile/`：编译示例；`swig/`：多语言绑定；`doc/`：文档。

### 拿它测试检测系统时能验证什么

纯软件库，电脑上直接编译运行，自带的 RMAP 字节流可以拿来做模糊测试。协议的包校验顺序、错误处理路径是检测状态处理类缺陷的好素材。定位：卫星总线方向的扩展测试对象（当前主测试对象之外）。
