# 开源嵌入式代码检测系统项目集（详细版）

> 用途：开发我们自己的嵌入式代码检测系统时的参考对象。以下 9 个（组）开源工具/平台都是近年嵌入式代码检测领域已成型、可下载使用的项目，信息核实于 2026-11-02。每个工具介绍它是什么、解决什么问题、项目里包含什么内容，以及对我们的检测系统开发有什么借鉴价值。

**术语说明**（正文中反复出现，先统一解释）：

- **静态分析**：不运行程序，直接读代码找问题（我们系统的主路线）。
- **动态分析**：把程序真正跑起来、喂给它输入，观察实际行为找问题。
- **抽象解释**：用数学近似的方法，推算程序里每个变量在运行时所有可能的取值范围——算得快且必然不漏，但结果偏"保守"。
- **符号执行**：用"未知数"代替真实输入去执行程序，让程序沿所有可能的路径走一遍，找出哪些路径会出事。
- **模型检查**：把"程序必须满足的性质"（比如不能越界）写成数学命题，交给求解器证明成立或不成立。
- **SMT 求解器**：判断复杂逻辑条件有没有解的数学引擎，是模型检查工具的核心部件。
- **MMIO（内存映射寄存器）**：嵌入式设备把外设（串口、定时器等）的控制开关映射成特定内存地址，读写这些地址就等于操作硬件。
- **外设建模**：用软件模型模拟硬件外设的行为，让"没有真硬件"的固件也能在电脑仿真器里跑起来。
- **中断**：硬件主动"打断"CPU 当前工作的机制（比如串口收到数据时叫醒 CPU），是嵌入式软件并发的根源，也是并发类缺陷的高发地。
- **竞态（数据竞争）**：两段代码不受保护地同时读写同一个数据，结果取决于执行的先后顺序——嵌入式里最隐蔽的缺陷类型之一。
- **Ghidra**：美国国家安全局（NSA）开源的逆向工程平台，把固件二进制还原成可读的函数和汇编。
- **反向切片**：从某条语句出发，倒着找出所有影响它执行结果的代码——不需要理解整个程序，只需要理解这一小块。

## 1. FirmXRay

- **仓库**：https://github.com/OSUSecLab/FirmXRay
- **许可**：MIT ｜ **开源时间**：2020 年（论文发表于顶级会议 ACM CCS 2020，俄亥俄州立大学）｜ 2024 年后基本停更
- **语言**：Java ｜ GitHub 78 星

### 是什么

**不运行程序**、直接从裸机固件的二进制文件里找出蓝牙协议配置错误的静态分析工具。它要解决的现实难题是：裸机固件没有标准入口（main 函数）、厂商 SDK（软件开发包）还是闭源的，传统分析工具拿到固件根本无从下手。它在三个真实平台（Nordic、TI 的蓝牙芯片固件）上找到了真实漏洞。

### 项目里有什么

- `src/`：主体，三步流水线——第一步自动推断固件的加载基址（裸机镜像没有文件头，地址全靠猜，它用"指针指向关系"来推断）；第二步从 SDK API 的调用点出发反向切片（只提取影响这个调用的代码，不用分析整个程序）；第三步在切片范围内模拟执行指令，算出固件传给 SDK 的具体配置数值；
- `base/`：基址推断组件；`dataset/`、`examples/`：测试固件和样例；
- 唯一依赖是 Ghidra（NSA 开源的逆向平台）编译出的一个 jar 包，部署极轻。

### 能给我们的检测系统带来什么

它是静态路线解决嵌入式两大老大难问题（没有 main 入口、SDK 闭源）的完整样板：**从"SDK 函数被调用的地方"入手分析，而不是从程序入口入手**；闭源 SDK 本体不需要读，只需要知道那些 API 的含义。这个思路可以直接移植到我们在 LLVM IR（编译器中间表示）上的分析。

## 2. P²IM / DICE / AIM（同一团队的外设建模"三件套"）

- **仓库**：https://github.com/RiS3-Lab/p2im （P²IM）｜ https://github.com/RiS3-Lab/DICE-DMA-Emulation （DICE）｜ https://github.com/bofeng17/AIM-Interrupt-Modeling （AIM）
- **许可**：自定义许可（见仓库）｜ **开源时间**：2020–2023（论文分别发表于 USENIX Security 2020、IEEE S&P 2021、IEEE TDSC 2023，加州大学河滨分校）｜ P²IM 主仓库 2023 年后停更
- **语言**：C / Python ｜ P²IM 149 星、DICE 67 星、AIM 33 星

### 是什么

三个一脉相承的工具，共同解决"**固件在电脑仿真器里跑不起来**"的问题：仿真器只模拟了处理器，固件一操作外设（读写 MMIO 寄存器）就卡死。三件套的做法是让仿真器在运行中**自动学习每个外设寄存器扮演什么角色**，然后按角色装作硬件作出反应：

- **P²IM**：把寄存器自动分成四类——配置型（初始化时写一次）、状态型（循环轮询读）、控制/数据型、输入型（外部数据来源），按类型注入不同行为；
- **DICE**：同一思路处理 DMA（不经 CPU 直接搬运数据的通道），自动识别"硬件往内存写数据"的通道；
- **AIM**：补上**中断**这块最难啃的骨头——自动学习"什么时候该触发哪个中断"，让依赖中断的异步代码（嵌入式软件的常态）在仿真中活起来，异步代码覆盖率达到原来的最高 11.2 倍。

### 项目里有什么

- `model_instantiation/`：寄存器分类器的实现（核心资产）；
- `qemu/`：改造过的 QEMU（开源仿真器），把分类器挂进去；
- `fuzzing/templates/`：模糊测试的种子和配置模板；
- `utilities/`：覆盖率统计与模型统计脚本；
- AIM 基于另一个知名分析平台 angr 实现，做动态符号执行。

### 能给我们的检测系统带来什么

**寄存器的"角色分类法"（配置/状态/控制数据/输入）是经过顶会验证的知识组织方式**——我们建寄存器知识库时直接照这个框架来：不同角色挂不同的检查规则（配置型查"重复配置"、状态型查"写只读位"）。AIM 证明了中断是检测嵌入式并发问题时绕不开的建模对象——这正是我们要做的"中断感知竞态检测"的理论参照。注意三件套都是动态路线，代码可当文献读，不必照搬。

## 3. Fuzzware

- **仓库**：https://github.com/fuzzware-fuzzer/fuzzware
- **许可**：Apache-2.0 ｜ **开源时间**：2022 年（论文发表于安全顶会 USENIX Security 2022）｜ 2026 年 6 月后边缘维护
- **语言**：Python + C ｜ GitHub 390 星

### 是什么

自动化"自配置"的固件模糊测试工具。它的核心洞察：固件对寄存器的大量读写其实是"无害的等待和确认"（读个状态位死等、清个完成标志），真正有意义的寄存器只是少数。于是它让模糊测试器先随便回答寄存器的读值，同时在后台分析每次寄存器访问"固件拿读到的值干了什么"——影响控制流的留下重点照顾，不影响的自动建模消除，如此循环，**硬件行为模型是自动学出来的，不用人工写**。

### 项目里有什么

- `fuzzware-emulator/`（子仓库）：基于 Unicorn（开源 CPU 仿真引擎）的单输入仿真器，负责把模糊测试的输入喂给寄存器读取；
- `modeling/`：MMIO 访问建模组件，对每次访问做符号执行判断"值是否影响控制流"；
- `fuzzware-pipeline/`（子仓库）：总编排——仿真器发现新寄存器访问 → 推给建模 → 新模型回灌仿真器 → 继续模糊测试，循环迭代；
- `examples/`：可直接跑的固件样例；`docs/`：配置优化、崩溃分析文档。

### 能给我们的检测系统带来什么

它的"**访问模式自动分类**"思想可以静态移植：在我们的 IR 上统计每个寄存器地址的读写模式（只读不写/固定写序列/写完不再读），自动给寄存器打上角色标签、生成"无副作用"白名单——让规则编写聚焦到少数关键寄存器，大幅降低知识库的建设成本。另外它的硬件模型是纯配置文件（YAML），"引擎与知识分离"的形态值得照抄。

## 4. CodeChecker

- **仓库**：https://github.com/Ericsson/codechecker
- **许可**：Apache-2.0 ｜ **开源时间**：2015 年 ｜ **状态**：持续活跃更新（爱立信官方维护 11 年）｜ GitHub 2,631 星
- **语言**：Python ｜ 文档齐全（codechecker.readthedocs.io）

### 是什么

爱立信出品的生产级静态分析管理平台。**它自己不做分析**，而是把 Clang Static Analyzer（LLVM 的官方分析器）、Clang-Tidy、Cppcheck、GCC 静态分析器、Facebook Infer 等五六个引擎的输出统一收进一个缺陷数据库，提供网页界面做告警浏览、去重、审阅、误报标记，并提供命令行和持续集成集成。在真实工业环境里维护了 11 年，是这个领域的工程化标杆。

### 项目里有什么

- **命令行工具链**：`CodeChecker log`（旁路监听整个编译过程，自动生成编译数据库）、`analyze`（调用各引擎分析）、`parse`/`store`（结果入库）；
- **Web 服务**：缺陷数据库（支持 PostgreSQL/SQLite）+ 网页界面——告警可按规则、严重级别、路径过滤，**两次分析可做 diff 对比**（新增了哪些告警、修复了哪些），误报可标记抑制并附评审意见；
- **工程适配能力**：能自动探测 GCC 交叉编译工程的配置并转换成分析器调用；支持增量分析（只重析改过的文件及其依赖）；
- 多种持续集成系统（GitLab/Gerrit/Jenkins）的评审集成。

### 能给我们的检测系统带来什么

我们的告警中心（告警浏览、采纳/拒绝、修复闭环）和它的定位同构，可以对照补全三点：**编译配置自动探测**（不真编译，只解析工程文件里的宏定义、头文件路径、目标架构——解决"嵌入式工程导不进来"的第一道门槛）、**增量分析**（只分析变更影响到的文件）、**跨版本告警差分**（对比两次运行，只报新增告警）。

## 5. ESBMC

- **仓库**：https://github.com/esbmc/esbmc
- **许可**：自定义开源许可（见仓库；商业使用有专门条款）｜ **开源时间**：2015 年（工具本身 2005 年起持续演进）｜ **状态**：持续活跃更新（核实当日仍在提交）｜ GitHub 537 星
- **语言**：C++

### 是什么

"高效基于 SMT 的上下文受限模型检查器"——名字直译了它的原理：把程序的检查条件交给 SMT 求解器（数学引擎）证明，逐层展开循环和调用直到能下结论。支持 C/C++，能证明的缺陷类型包括越界、除零、溢出、内存泄漏等。它在**国际软件验证竞赛 SV-COMP（Software Verification Competition，全球验证工具的年度竞技场）中多次获奖**，是开源模型检查工具里的头部选手。

### 项目里有什么

- 完整的模型检查器实现（C/C++ 前端、SMT 求解接口、k-归纳证明——一种"先证小区间成立，再逐步扩大到全体"的数学证明方法）；
- 支持 Linux/macOS/Windows，提供 Docker 镜像；
- 大量回归测试用例。

### 能给我们的检测系统带来什么

远期定位：如果我们要给自动修复加一道**形式化复核**（不依赖大模型、有数学保证的"补丁验证器"），ESBMC 是现成的开源选项。当前阶段的主要价值是理解"验证器驱动修复"闭环的上游——它输出的反例（违反性质的具体路径和变量值）是喂给大模型修复的标准输入形态。

## 6. esbmc-ai

- **仓库**：https://github.com/esbmc/esbmc-ai
- **许可**：双许可模式（开源许可 + 商业许可，见仓库 LICENSE）｜ **开源时间**：2023 年 ｜ **状态**：**已归档停止开发**，官方声明后继为商业产品 Entoli（byterepair.io）｜ GitHub 43 星
- **语言**：Python

### 是什么

"检测 → 大模型修复 → 回归验证"闭环的第一个完整开源实现：把 ESBMC 输出的技术性反例翻译成大模型能理解的修复任务，让大模型生成补丁，再回到 ESBMC 重新验证——不通过就带着失败原因重试。**大模型只负责生成补丁，"判定补丁对不对"的权力始终在形式化验证器手里**。这个项目被商业化的结局，等于行业给"检测 + LLM 修复 + 验证闭环"这条路线投了信任票——我们系统的一键修复闭环走的正是同一条路，差异点在嵌入式场景和硬件语义。

### 项目里有什么

- `esbmc_ai/`：编排主体——命令分发、修复工作流（读反例 → 组装提示词 → 调大模型 → 应用补丁 → 重跑 ESBMC 验证 → 失败带反馈重试）；
- 插件化（Addon）架构：新命令、新检测器、新修复策略可以即插即用；
- `samples/`、`tests/`、Docker 镜像、完整的文档站。

### 能给我们的检测系统带来什么

它是唯一公开了完整"LLM 修复工作流"源码的项目，三处可以直接对照：**翻译层设计**（给大模型的输入不该是原始告警 JSON，而是结构化的"缺陷模式 + 相关代码片段 + 触发条件"）、**失败反馈重试**（补丁验证失败时把失败原因喂回大模型再试）、**插件化扩展**（后续接军用标准规则包、雷达场景包时可参照）。读快照即可，仓库不会再更新。

## 7. Goblint

- **仓库**：https://github.com/goblint/analyzer
- **许可**：MIT ｜ **开源时间**：2011 年（开源维护 15 年）｜ **状态**：持续活跃更新 ｜ GitHub 254 星
- **语言**：OCaml ｜ 文档齐全（goblint.readthedocs.io）

### 是什么

面向 C 语言并发程序的抽象解释分析器，**国际验证竞赛 SV-COMP 并发赛道的常胜将军**。它的招牌技术是"每线程模块化"分析：每个线程（执行流）单独计算不变量，通过共享变量的抽象值交换信息，避免"所有线程组合状态"的爆炸式增长。但要泼一盆冷水：**它的并发模型建立在 pthread（桌面程序的多线程库）上，对嵌入式的真实并发单位——中断服务程序和实时操作系统任务——是系统性漏报的**（这一点我们调研报告 V1.2 第 346 页已论证引用）。

### 项目里有什么

- `src/`：OCaml 实现的抽象解释引擎——可插拔的抽象域（区间、位域、锁集合等，可组合使用）与不动点求解框架；
- `conf/`、`tests/`、`bench/`：配置、回归测试与基准；
- 通过 opam（OCaml 包管理器）或 Docker 安装。

### 能给我们的检测系统带来什么

**框架可学，模型必须换**：它"每个并发单元独立分析、在共享数据点交换信息"的算法骨架，正是我们做中断感知竞态检测要用的骨架——把"线程 + 锁"换成"中断服务程序 + 中断优先级"即可。它 15 年持续维护的抽象域工程组织，也是我们做寄存器值域分析的参考。注意它是纯学术风格的 OCaml 工程，代码本身不移植，学思想。

## 8. angr（了解即可，不投入）

- **仓库**：https://github.com/angr/angr
- **许可**：BSD-2-Clause ｜ **开源时间**：2015 年 ｜ **状态**：持续活跃更新 ｜ GitHub 9,277 星
- **语言**：Python

### 是什么

功能最全的开源**二进制分析平台**：反汇编、控制流恢复、符号执行、仿真执行一应俱全，学术界大量论文（包括上面的 AIM）拿它当底座。

### 能给我们带来什么

我们走源码/中间表示路线，不做二进制逆向，所以 angr 整体不适用。但两个衍生事实值得知道：它是 P²IM 团队和 AIM 的实现底座（说明"仿真 + 符号执行"组合的行业标准做法）；它的 Python API 设计被广泛模仿，读文档有助于理解符号执行概念。

## 9. Karonte（了解即可，不投入）

- **仓库**：https://github.com/ucsb-seclab/karonte
- **许可**：BSD-2-Clause ｜ **开源时间**：2019 年（论文发表于 IEEE S&P 2020，加州大学圣芭芭拉分校）｜ **状态**：2021 年后停止更新 ｜ GitHub 435 星
- **语言**：Python

### 是什么

针对"多芯片固件"（路由器、摄像头这类由多个固件协作的设备）的静态分析工具，追踪数据如何跨固件边界流动来发现漏洞。

### 能给我们带来什么

它的场景（多二进制协作固件）我们不涉及，且已停更 5 年——只在论文相关工作里引用一句即可。它更重要的价值是个**反面教材**：顶会论文的开源工具在发表后 1–3 年内停止维护是普遍规律（本清单里 FirmXRay、P²IM、Karonte 皆是），这反过来印证了我们"规则库 + 大模型降低维护成本"路线的合理性。
